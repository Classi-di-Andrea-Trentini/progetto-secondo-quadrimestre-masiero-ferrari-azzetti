# Database Schema

Schema file: `server/prisma/schema.prisma`
Init SQL: `database/init/001_schema.sql`

PostgreSQL 16. All primary keys are UUIDs generated by `gen_random_uuid()`.

## Users and sessions

**users** — the main user table. Notable fields: `password_hash` (bcrypt), `is_active` (soft-disable without deleting), `deleted_at` (soft delete), `email_verified_at` (null until verified), `newsletter_opt_in`.

**sessions** — one row per active login. Fields: `token_hash` (SHA-256 of the raw JWT token, for session invalidation), `expires_at`, `ip_address`, `user_agent`. When the user logs out, the row is deleted. When the user changes their password, all other sessions are deleted.

**email_verifications** — used for both email verification and email change confirmation. The `token` field holds a JWT signed with `JWT_SECRET`. The `used_at` field is set when the link is clicked so the link cannot be used twice.

**password_resets** — exists in the schema but has no active flow in the codebase yet.

**notifications** — in the schema, not yet exposed via API.

## Catalogue

**categories** — supports a parent/child hierarchy via `parent_id` (self-referencing FK with SET NULL on delete). Flat or two-level trees both work. `sort_order` controls display order.

**tags** — free-form labels. Many-to-many with products via `product_tags`.

**products** — the core product record. `base_price` is a `Decimal(10,2)`. `avg_rating` is a `Decimal(3,2)` recomputed by the reviews service. `sold_count` is incremented atomically by the checkout transaction.

**product_variants** — each row is one stockable unit (a size + color combination). `sku` is unique across the entire table. `price_override` is used when a variant costs more or less than the base price. `stock_qty` is decremented on each order.

**product_images** — images for a product. `is_cover = true` marks the primary listing image. `sort_order` determines gallery order. `variant_id` is optional and links an image to a specific color variant.

**discounts** — can be applied at product level or variant level. Type is either `percentage` or `fixed_amount`. `is_active` and optional date range fields allow scheduling. The products service always takes only the first active discount (`take: 1`).

## Commerce

**wishlists** — a unique constraint on `(user_id, product_id, variant_id)` prevents duplicates. The toggle logic in the service queries by all three fields.

**carts** — one cart per user (unique on `user_id`). References a promo code and gift card if applied.

**cart_items** — one row per variant in the cart. Unique on `(cart_id, variant_id)`.

**orders** — the financial record. Stores `subtotal`, `discount_total`, `shipping_cost`, and the final `total`. References the delivery address, promo code, and gift card used.

**order_items** — snapshot of what was ordered. Stores `product_name`, `variant_label`, `sku_snapshot` at the time of purchase so the order history is preserved even if the product is later changed or deleted. `unit_price` and `line_total` are also snapshotted.

**order_status_history** — append-only log of status changes. Each transition from `pending` to `paid` etc. is recorded here.

**payments** — one row per payment attempt. In the current mock implementation, one succeeded payment is created per order.

**promo_codes** — supports both percentage and fixed amount discounts. `max_uses` is global, `max_uses_per_user` is per-account. `min_order_amount`, `max_discount_cap`, date range fields, and optional restriction to a specific product or category.

**promo_code_uses** — audit table recording which user used which code on which order.

**gift_cards** and **gift_card_transactions** — in the schema but no API endpoints exist yet.

---

## Post-purchase

**reviews** — unique on `(user_id, product_id)` so one review per product per user. `is_verified` is set if the user has a delivered/completed order containing that product. `helpful_count` is a denormalised counter updated atomically.

**review_helpful_votes** — composite PK `(review_id, user_id)` prevents double-voting.

**review_replies** — admin responses to reviews.

**returns** — one return request per order (enforced in the service by checking for existing non-rejected returns). `status` progresses from `requested` through the return workflow.

**return_items** — line items within a return. References the original `order_item` and a quantity (which can be less than the ordered quantity for partial returns).

## Foreign key delete rules

Most FKs use the default behaviour (RESTRICT — delete is blocked if children exist). Cascade deletes are used where a child record has no meaning without its parent:

- `product_variants` → `products`: CASCADE (deleting a product deletes its variants)
- `product_images` → `products`: CASCADE
- `discounts` → `products`/`product_variants`: CASCADE
- `product_tags` → `products`/`tags`: CASCADE
- `order_items` → `orders`: CASCADE
- `return_items` → `returns`: CASCADE
- `review_helpful_votes` → `reviews`: CASCADE
- `review_replies` → `reviews`: CASCADE
- `sessions` → `users`: CASCADE
- `email_verifications` → `users`: CASCADE
- `notifications` → `users`: CASCADE

The `categories.parent_id` self-reference uses SET NULL, so deleting a parent category does not delete its children — it orphans them as root categories.

`promo_codes.applies_to_product` and `applies_to_category` also use SET NULL, so deleting a product or category does not invalidate the promo code — it just makes the restriction go away.
